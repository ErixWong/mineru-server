# 查询和获取结果端点设计确认

**问题**: 查询状态和获取结果是否是同一个端点？

**答案**: ✅ **是的！在 MCP/API 中合并为同一个端点！**

---

## 1. MCP Tools - get_task（合并端点）

**Tool**: `get_task(task_id, return_md=True/False)`

**智能逻辑**：

根据任务状态，自动返回不同内容：

| 任务状态 | return_md | 返回内容 | 说明 |
|---------|----------|---------|------|
| **pending** | 任意 | 状态 + 提示 | 任务等待中，无法获取结果 |
| **processing** | 任意 | 状态 + 提示 | 任务处理中，无法获取结果 |
| **completed** | False | 状态 + 提示 | 仅返回状态，提示用户获取结果 |
| **completed** | True | 状态 + Markdown | ✅ 同时返回状态和结果 |
| **failed** | 任意 | 状态 + 错误 | 任务失败，返回错误信息 |

---

### 代码实现

```python
@mcp.tool()
async def get_task(
    task_id: str,
    return_md: bool = True,  # ✅ 控制是否返回结果
) -> dict[str, Any]:
    """Get task status and optionally results"""
    
    # 获取任务状态
    status_info = await client.get_task_status(task_id)
    task_status = status_info.get("status")
    
    # 根据状态返回不同内容
    if task_status in ("pending", "processing"):
        # 仅返回状态
        return {
            "task_id": task_id,
            "status": task_status,
            "message": "Task is processing"
        }
    
    if task_status == "completed":
        if return_md:
            # ✅ 返回状态 + 结果
            result = await client.get_task_result(task_id)
            return {
                "task_id": task_id,
                "status": "completed",
                "markdown": aggregate_markdown(result)  # ✅ 包含结果
            }
        else:
            # 仅返回状态
            return {
                "task_id": task_id,
                "status": "completed",
                "message": "Use return_md=true to get results"
            }
    
    if task_status == "failed":
        return {
            "task_id": task_id,
            "status": "failed",
            "error": "..."
        }
```

## 2. REST API - /tasks/{id}（合并端点）

**Endpoint**: `GET /tasks/{task_id}?return_md=true/false`

**逻辑与 MCP Tools 相同**，智能返回状态或结果。

---

### 代码实现

```python
@app.get("/tasks/{task_id}")
async def get_task(
    task_id: str,
    return_md: bool = Query(default=True),  # ✅ Query 参数控制
):
    """Get task status and optionally results"""
    
    validated_task_id = validate_task_id(task_id)
    status_info = await client.get_task_status(validated_task_id)
    task_status = status_info.get("status")
    
    if task_status in ("pending", "processing"):
        return JSONResponse(
            status_code=200,
            content={
                "task_id": validated_task_id,
                "status": task_status,
                "message": "..."
            }
        )
    
    if task_status == "completed":
        if not return_md:
            # 仅状态
            return {
                "task_id": validated_task_id,
                "status": "completed",
                "message": "..."
            }
        
        # ✅ 状态 + 结果
        result = await client.get_task_result(
            task_id=validated_task_id,
            return_md=True,
            return_images=False,
        )
        
        return {
            "task_id": validated_task_id,
            "status": "completed",
            "markdown": aggregate_markdown(result)  # ✅ 包含结果
        }
```

---

### 使用示例

## 3. MinerU Native API - 分离端点

**对比**: MinerU 原生 API 使用**分离端点**

| Endpoint | 功能 | 说明 |
|----------|------|------|
| `GET /mineru_api/tasks/{id}` | 仅查询状态 | ✅ 仅返回状态，不包含结果 |
| `GET /mineru_api/tasks/{id}/result` | 仅获取结果 | ✅ 仅返回结果（JSON/ZIP） |

**优势**：
- ✅ 状态查询轻量（不加载结果）
- ✅ 结果获取灵活（可选择 JSON 或 ZIP）

**劣势**：
- ⚠️ 需要两次请求（先查询状态，再获取结果）
- ⚠️ 实现更复杂

## 4. 设计对比

| API | 查询状态 | 获取结果 | 端点数 | 设计优势 | 设计劣势 |
|-----|---------|---------|-------|---------|---------|
| **MCP Tools** | ✅ 合并 | ✅ 合并 | 1 个 | ✅ 简单易用<br>✅ 单次请求 | ⚠️ 查询状态时可能加载结果 |
| **REST API** | ✅ 合并 | ✅ 合并 | 1 个 | ✅ 简单易用<br>✅ 可控制是否返回结果 | - |
| **MinerU Native** | ❌ 分离 | ❌ 分离 | 2 个 | ✅ 状态查询轻量<br>✅ 结果格式灵活 | ⚠️ 需两次请求 |

---

## 5. 智能端点优势

**MCP/API 合并端点的优势**：

1. **✅ 简化使用**：
   - 用户只需记住一个端点
   - 无需区分状态查询和结果获取

2. **✅ 自动适配**：
   - 任务未完成 → 仅返回状态
   - 任务完成 → 自动返回结果
   - 无需用户手动判断

3. **✅ 可控灵活**：
   - `return_md=true` → 获取结果
   - `return_md=false` → 仅状态
   - 用户可精确控制

4. **✅ 符合预期**：
   - 用户查询任务 → 期望知道状态 + 是否完成
   - 如果完成 → 自动返回结果（一次请求）

## 6. 最佳实践建议

### 6.1 MCP/API 使用建议

**推荐流程**：
```
submit_task → 提交任务
↓
get_task(return_md=false) → 轮询状态（轻量）
↓ (pending/processing)
get_task(return_md=false) → 继续轮询
↓ (completed)
get_task(return_md=true) → 获取结果（一次请求）
↓
get_images(task_id) → 获取图片（如果需要）
```

**优化**：
- 轮询时使用 `return_md=false`（轻量查询）
- 完成后使用 `return_md=true`（一次获取结果）

---

### 6.2 MinerU Native 使用建议

**流程**：
```
POST /tasks → 提交任务
↓
GET /tasks/{id} → 查询状态（轻量）
↓ (pending/processing)
GET /tasks/{id} → 继续查询
↓ (completed)
GET /tasks/{id}/result → 获取结果（ZIP 或 JSON）
```

**特点**：
- 状态查询始终轻量（不加载结果）
- 结果获取独立端点（格式灵活）

## 7. 总结

### ✅ 确认结论

**MCP/API**：
- ✅ 查询和获取结果合并为同一个端点
- ✅ 智能设计：自动根据状态返回不同内容
- ✅ 用户可控：`return_md` 参数精确控制

**MinerU Native**：
- ❌ 分离端点：查询状态 + 获取结果（独立）
- ✅ 状态查询轻量
- ✅ 结果格式灵活（JSON/ZIP）

- ✅ **性能优化** - 状态查询轻量
